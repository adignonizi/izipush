izipush · proposition de déploiement

Architecture AWS izipush

Six services applicatifs, trois systèmes de données. La transposition est directe — aucun d'eux n'a besoin d'être réécrit — mais deux contraintes de DocumentDB doivent être traitées avant la migration, pas découvertes pendant.

Le schéma

Trois zones de disponibilité, trois étages de sous-réseaux. Seul l'équilibreur est exposé ; les tâches applicatives n'ont pas d'adresse publique et les données encore moins.

Décisions à trancher avant la migration

Vérifiées contre le code et la documentation AWS, pas supposées. Les deux premières sont bloquantes.

bloquant

Cluster à instances, jamais cluster élastique

DocumentBD propose deux formes : le cluster à instances et le cluster élastique (partitionné). Le second ne gère pas les index partiels. Le DAL en compte vingt — sur les attributs segmentables de l'abonné, sur les événements, sur l'activité. Un cluster élastique les refuserait à la création.

Vérifié — table « Index properties » de la documentation DocumentDB : Partial vaut No en 3.6 et 4.0, Yes en 5.0 et 8.0, No pour Elastic cluster. Donc DocumentDB 8.0 en cluster à instances convient — je l'avais d'abord cru incompatible, la documentation dit le contraire.

bloquant

retryWrites=false dans la chaîne de connexion

DocumentDB ne gère pas les écritures réessayables, et le pilote Node les active par défaut depuis MongoDB 4.2. Sans ce paramètre, chaque écriture échoue sur Unrecognized field: 'txnNumber' — l'application démarre, se connecte, et ne peut rien écrire.

À faire — le paramètre n'est positionné nulle part dans le dépôt aujourd'hui. Il doit être ajouté à MONGO_URL au moment de la bascule, avec le certificat rds-combined-ca-bundle.pem pour le TLS.

attention

ElastiCache en mode non cluster

BullMQ exige que les clés d'une même file résident sur le même emplacement de hachage. En mode cluster, elles se répartissent et les opérations atomiques échouent. Novu expose bien un drapeau IS_IN_MEMORY_CLUSTER_MODE_ENABLED, mais il suppose une configuration de clés adaptée qui n'est pas la nôtre.

Recommandation — un nœud primaire et un réplica en bascule automatique, mode non cluster. Six files à servir : standard, trigger-handler, process-subscriber, ws_socket_queue, inbound-parse-mail, metric-active-jobs.

sans risque

Aucune étape d'agrégation incompatible

DocumentDB ne gère ni $facet, ni $graphLookup, ni $setWindowFields, ni $unionWith, ni $bucketAuto. C'est la cause la plus fréquente d'échec d'une migration MongoDB vers DocumentDB.

Vérifié — aucune de ces étapes n'apparaît dans libs/dal, libs/application-generic ni dans les trois applications. Les transactions multi-documents et les index TTL, eux, sont pris en charge.

choix

Amazon MQ plutôt que SQS ou EventBridge

Izichange publie déjà sur un échange RabbitMQ par sujet, et crm-ingest consomme avec des liaisons par motif. Amazon MQ conserve ce contrat tel quel. Passer à SQS imposerait de réécrire l'émission côté Izichange et la consommation côté izipush, pour un gain nul à ce volume.

À revoir si le débit dépasse ce qu'un courtier gère confortablement, ou si vous voulez abandonner RabbitMQ chez Izichange. Ce n'est pas le cas aujourd'hui.

attention

Le worker se met à l'échelle sur la file, pas sur le processeur

Un worker qui attend des réponses de FCM, d'APNs et des fournisseurs d'email consomme peu de processeur tout en accumulant du retard. Une règle basée sur le processeur ne déclencherait jamais. Il faut publier la profondeur des files BullMQ comme métrique CloudWatch et s'en servir comme signal de mise à l'échelle.

Conséquence — le worker n'est derrière aucun équilibreur et n'a pas de sonde de santé HTTP ; sa santé se lit dans le retard de traitement.

Découpage réseau

Trois étages, trois niveaux d'exposition. Rien de ce qui porte des données n'a de route sortante.

Étage 1 — public

Sous-réseaux publics

  • Application Load Balancer
  • Passerelle NAT, une par zone

Seul point d'entrée. Le certificat TLS vient d'ACM, renouvelé sans intervention.

Étage 2 — privé

Tâches ECS Fargate

  • api, ws, izinews — joignables par l'équilibreur
  • worker, crm-ingest — joignables par personne

Sortent par la passerelle NAT pour joindre FCM, APNs et les fournisseurs d'email.

Étage 3 — isolé

Données

  • DocumentDB
  • ElastiCache
  • Amazon MQ

Aucune route vers Internet. Accessibles par groupe de sécurité depuis l'étage 2 seulement.

difficulté

Les jetons expirent en 12 heures — EAS Build ne tourne pas chez vous

CodeArtifact n'accepte que des jetons d'autorisation d'une durée maximale de douze heures. Une construction mobile s'exécute sur l'infrastructure d'Expo, qui ne peut pas demander ce jeton toute seule : il lui faut des identifiants AWS.

Deux voies — soit déposer les clés d'un utilisateur IAM en lecture seule comme secrets EAS, installer l'interface AWS dans le crochet eas-build-pre-install et y lancer aws codeartifact login --tool npm ; soit laisser le mobile sur GitHub et ne basculer que les constructions serveur. Le crochet existe déjà dans package.json : il réécrit aujourd'hui les URL git avec $GITHUB_TOKEN, c'est le même emplacement.

gain

Une connexion externe met aussi npmjs en cache

Un dépôt CodeArtifact peut se brancher en amont sur npmjs.com. Les paquets publics y sont alors copiés à la première demande. Vos constructions cessent de dépendre de la disponibilité de npmjs, et un paquet retiré du registre public reste installable.

Utile ici — le monorepo installe plusieurs centaines de dépendances à chaque image. C'est le bénéfice le plus immédiat, indépendamment du SDK.

à prévoir

Permissions IAM

Lire : codeartifact:GetAuthorizationToken, GetRepositoryEndpoint, ReadFromRepository. Publier, en plus : PublishPackageVersion, PutPackageMetadata.

Souvent oublié — sts:GetServiceBearerToken est également requis, avec la condition sts:AWSServiceName = codeartifact.amazonaws.com. Sans elle, l'obtention du jeton échoue alors que les permissions CodeArtifact semblent complètes.

à faire

Renommer le paquet

@gittestmag/izipush-sdk porte le nom d'un compte GitHub de test. Le passage à CodeArtifact est le bon moment pour adopter une portée qui vous appartient, par exemple @izichange/izipush-sdk.

Conséquence — les imports changent dans izipay-pos et dans izinews, et la version repart proprement. À faire en une fois, pas progressivement.

Ce que la proposition ne couvre pas

Pour que vous sachiez ce qu'il reste à décider.

à chiffrer

Dimensionnement et coût

Aucun prix ici : il dépend de la taille des instances DocumentDB, du volume d'envois et de la rétention des journaux. À établir une fois le volume cible connu.

à décider

Reprise après incident

Les instantanés DocumentDB et la restauration à un instant donné couvrent la base. Reste à fixer la durée de rétention acceptable et si une seconde région est nécessaire.

à préparer

Migration des données

Les index partiels et TTL doivent être recréés après import : mongorestore ne restaure pas la base admin, et les rôles utilisateurs sont à refaire.
