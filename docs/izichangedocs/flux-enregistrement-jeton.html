Enregistrement d'un jeton push

Quatre façons de faire parvenir un jeton FCM à izipush. Elles ne diffèrent que sur un point — qui prouve que l'abonné est bien celui qu'il prétend être — et c'est ce point qui décide de tout le reste : le nombre d'appels, le travail côté passerelle, et si un tiers peut détourner les notifications d'un client.

Les acteurs

Quatre, et c'est la frontière entre les deux du milieu qui porte toute la question. La passerelle connaît la session de l'utilisateur ; l'app cliente, elle, ne peut rien prouver par elle-même — tout ce qu'elle embarque est lisible par qui démonte le paquet.

Le point de départ. applicationIdentifier est embarqué dans le bundle de l'app : on l'extrait d'un APK en quelques minutes, et il est en clair dans le JavaScript d'une page web. C'est une clé de routage — elle dit à izipush de quel environnement il s'agit — et non une preuve d'identité. Toute la suite découle de là.

Flux A — le JWT d'abonné, ce qui tourne aujourd'hui

Le SDK échange l'identifiant public contre un jeton signé, puis s'en sert pour enregistrer. C'est le chemin par défaut du SDK quand aucun sessionToken ne lui est fourni. 

sequenceDiagram
  autonumber
  participant C as App cliente — SDK
  participant G as Passerelle Izichange
  participant F as Firebase FCM
  participant N as izipush

  C->>G: POST /login
  G-->>C: 200 + session
  C->>F: getToken
  F-->>C: jeton FCM
  C->>N: POST /v1/widgets/session/initialize
applicationIdentifier + subscriberId
  N-->>C: 201 + JWT abonné — valable 15 jours
  C->>N: PUT /v1/widgets/credentials
Authorization Bearer JWT
  N-->>C: 200 — jeton enregistré
Le coût réel. Les étapes 5 et 6 ne se rejouent pas à chaque enregistrement : le JWT vit quinze jours et le SDK le réutilise tel quel dès qu'on lui passe un sessionToken. C'est donc un appel par connexion, pas un par notification ni un par démarrage. Sans sessionToken, en revanche, le SDK refait la paire à chaque enregistrement — c'est ce cas-là, et lui seul, qui est coûteux.

Flux B — le JWT voyage avec le login

Même mécanique, mais l'aller-retour disparaît du client : la passerelle ouvre la session izipush pendant qu'elle traite une connexion qu'elle traite déjà, et joint le jeton à sa réponse.

Flux C — serveur à serveur, sans aucun JWT

Le SDK s'arrête au jeton FCM et le remet à l'app hôte. C'est la passerelle qui enregistre, avec sa clé secrète. Le JWT et le HMAC disparaissent tous les deux. 

sequenceDiagram
  autonumber
  participant C as App cliente — SDK
  participant G as Passerelle Izichange
  participant F as Firebase FCM
  participant N as izipush

  C->>G: POST /login
  G-->>C: 200 + session
  C->>F: getToken
  F-->>C: jeton FCM
  C->>G: POST /push/token
jeton + providerId — sur la session authentifiée
  Note over G: le subscriberId est lu dans la session
jamais dans le corps de la requête
  G->>N: PATCH /v1/subscribers/ID/credentials
Authorization ApiKey — clé API d'environnement
  N-->>G: 200
  G-->>C: 204
Même usecase que la route widget. PATCH /v1/subscribers/ID/credentials appelle UpdateSubscriberChannel avec isIdempotentOperation: false, exactement comme PUT /v1/widgets/credentials : même union dédoublonnée des jetons, même remplacement par appareil, même plafond. Rien ne se dégrade — seule la source de l'identité change.

Deux réserves. Il faut une route /push/token sur la passerelle. Et l'abonné doit préexister, sinon la route répond BadRequest : l'ingestion CRM le crée sur account.*, mais un inscrit de la minute précédente peut arriver avant son événement — prévoir un réessai, ou un POST /v1/subscribers en amont.

Flux D — l'applicationIdentifier seul

Techniquement faisable en modifiant le fork — une quinzaine de lignes. Voici ce que ça autorise, et pourquoi le problème n'est pas la faille elle-même mais son silence. 

sequenceDiagram
  autonumber
  actor A as Attaquant
  actor V as Victime
  participant N as izipush

  A->>A: extrait applicationIdentifier du bundle — public
  A->>N: PUT /credentials
subscriberId de la victime + son propre jeton FCM
  N-->>A: 200 — rien ne distingue cet appel d'un légitime
  Note over N: la route fait l'UNION des jetons
celui de la victime n'est pas remplacé
  N->>V: notification — reçue normalement
  N->>A: la même notification
  Note over A,V: la victime ne constate aucune anomalie
l'interception ne laisse aucune trace
Ce qui fuite. Montants de transaction, décisions KYC, alertes de sécurité. Pour un service de transfert d'argent, ce n'est pas une gêne théorique.

Et subscriberId n'est pas un secret. C'est l'identifiant Keycloak de l'utilisateur — il circule dans les réponses d'API, les journaux, les tickets de support. Une authentification ne peut pas reposer sur le fait de connaître un identifiant : c'est précisément la différence entre identifier et authentifier.

Le vrai arbitrage. D est la seule option qui ne demande rien à la passerelle — c'est son unique avantage. B et C demandent le même genre de travail, donc autant prendre C, qui supprime le JWT pour de bon.

Ce que l'API accepte réellement

Relevé dans le code, pas déduit. C'est ce qui rend D impossible sans modifier le fork.

RouteGardeAccepte des credentials
POST /v1/widgets/session/initialize aucune non — subscriberId, applicationIdentifier, email, firstName, lastName, phone, hmacHash
PUT /v1/widgets/credentials subscriberJwt oui
PATCH /v1/subscribers/ID/credentials ApiKey — clé d'environnement oui, en ajout
PUT /v1/subscribers/ID/credentials ApiKey — clé d'environnement oui, en remplacement
les 22 autres routes widgets subscriberJwt —
Une seule route sans garde sur les vingt-quatre du contrôleur widgets, et elle n'accepte pas de deviceTokens — on ne peut donc pas s'en servir pour enregistrer un jeton au passage. Les stratégies d'authentification disponibles sont apikey, jwt, subscriber-jwt et github : aucune n'est fondée sur l'applicationIdentifier, qui n'est d'ailleurs reconnu dans aucun autre contrôleur de l'API.

Après l'enregistrement — l'envoi et les retours

Pour situer le reste de la chaîne. C'est la partie qui explique la différence entre « envoyé » au tableau de bord et « reçu » sur l'appareil. 

sequenceDiagram
  autonumber
  participant W as Worker izipush
  participant F as Firebase FCM
  participant D as Appareil — SDK
  participant A as API izipush

  W->>F: sendEachForMulticast — un message par jeton
  F-->>W: accusé jeton par jeton
  Note over W: « Message sent » — FCM a accepté
ne prouve PAS que l'appareil a reçu
  F->>D: notification
  D->>A: POST /push-delivered
  Note over A: « Message delivered » — l'appareil confirme
raw.source = foreground ou background
  D->>A: POST /push-opened — au tap
  Note over A: seen + read + engagement CRM si campagne
À lire dans le journal d'activité. Un abonné dont toutes les livraisons portent foreground ne reçoit que lorsqu'il regarde l'application — son service worker ou sa tâche de fond ne fonctionne pas. Et une ligne d'erreur n'empêche pas le succès : le worker envoie un message par jeton, donc un jeton périmé échoue pendant que les autres aboutissent.
