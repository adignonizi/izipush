Izichange — izipush

@gittestmag/izipush-sdk

Un seul package pour brancher le push (Android, iOS, Web) sur izipush. Il gère l'autorisation de notification, le jeton, son enregistrement, son renouvellement, l'affichage et les statistiques d'ouverture — l'app hôte n'a que deux ou trois fonctions à appeler.

01

Ce que le SDK fait, et ce qu'il ne fait pas

Pour savoir tout de suite ce qui reste à la charge de l'app.

Il s'en charge

  • Demander l'autorisation de notification, ou enregistrer un jeton que l'app détient déjà.
  • Enregistrer le jeton sur le profil du client côté izipush, et le ré-enregistrer à chaque rotation.
  • Afficher les notifications reçues — Firebase n'affiche jamais rien tout seul, ni au premier plan, ni en arrière-plan, ni app fermée. C'est le piège classique, et il est traité.
  • Signaler au CRM l'appui sur une notification de campagne, sur les deux plateformes.

À la charge de l'app hôte

  • L'authentification. Le SDK ne sait pas qui est l'utilisateur : il faut lui passer l'identifiant du compte connecté, jamais un identifiant généré côté client.
  • Le calcul du hmacHash, côté serveur (section 03).
  • Le moment de la demande d'autorisation et l'écran qui l'explique (section 09).
  • Le contenu des notifications : il vient des workflows izipush, pas du SDK.
  • La navigation à l'appui sur une notification (deep-link), si le produit en a besoin.
Le même identifiant partout Le userId passé au SDK doit être exactement celui publié dans les événements métier (userId des messages RabbitMQ). C'est ce qui fait converger le profil push et le profil enrichi par le CRM sur un seul et même client. Deux identifiants différents produisent deux profils, donc deux fois chaque campagne.

03

Comment le SDK parle à izipush

Aucun serveur intermédiaire, et jamais la clé secrète d'environnement côté client.

Le SDK utilise le flux public de Novu — le même que le widget notification center — plutôt que les routes protégées par clé secrète :

  1. POST /v1/widgets/session/initialize — avec l'identifiant public de l'environnement (applicationIdentifier, sans risque à embarquer côté client), obtient un JWT limité à un seul abonné.
  2. PUT /v1/widgets/credentials — authentifié par ce JWT, enregistre le jeton push. Le JWT empêche un appelant de toucher aux identifiants d'un autre abonné que le sien.

Mode sécurisé (HMAC)

Si le mode sécurisé est actif sur l'environnement visé — recommandé, et déjà le cas en production — l'étape 1 exige un hmacHash calculé côté backend de l'app hôte, jamais côté client. Sans lui, quiconque connaît un subscriberId peut obtenir une session en son nom et détourner ses notifications.

Backend de l'app hôte (Node)

import { createHmac } from 'crypto';

// subscriberId = l'identifiant interne de l'utilisateur authentifié
const hmacHash = createHmac('sha256', process.env.NOVU_API_KEY)
  .update(subscriberId)
  .digest('hex');

// renvoyé à l'app, avec applicationIdentifier et novuApiUrl
res.json({ hmacHash });

05

Intégration React Native (Android + iOS)

Metro résout automatiquement dist/index.native.js.

Prérequis

  1. Un projet Firebase avec une app Android et une app iOS enregistrées — le même que celui du web.
  2. google-services.json (Android) dans android/app/.
  3. GoogleService-Info.plist (iOS) ajouté au projet Xcode.
  4. iOS uniquement — la clé APNs (.p8) ou le certificat téléversé dans la console Firebase (Paramètres du projet > Cloud Messaging). Sans elle, Firebase ne peut pas atteindre APNs : le jeton s'obtient, mais aucun envoi n'arrive.
  5. Le plugin Gradle Firebase appliqué (voir la documentation de @react-native-firebase/app).
  6. Permission Android déclarée : android.permission.POST_NOTIFICATIONS.

index.js — avant AppRegistry, jamais dans un composant

import { AppRegistry } from 'react-native';
import App from './App';
import { name as appName } from './app.json';
import { registerBackgroundHandler } from '@gittestmag/izipush-sdk';

registerBackgroundHandler({
  novuApiUrl: 'https://<host-izipush>/api',
  applicationIdentifier: '<identifiant public de l’environnement>',
});

AppRegistry.registerComponent(appName, () => App);
Sans cet appel, rien ne s'affiche app fermée Firebase exige ce gestionnaire au niveau module pour pouvoir réveiller l'app. Placé dans un composant, il n'est jamais enregistré à temps — et les notifications arrivent sans jamais être visibles.

Après authentification de l'utilisateur

import { initPush } from '@gittestmag/izipush-sdk';

const { hmacHash } = await backend.getPushSession(currentUser.id);

const subscription = await initPush(currentUser.id, {
  novuApiUrl: 'https://<host-izipush>/api',
  applicationIdentifier: '<identifiant public de l’environnement>',
  hmacHash,
});

if (subscription === null) {
  // autorisation refusée — proposer de la réactiver dans les réglages du système
}

Intégration Web

Les bundlers web résolvent dist/index.js. Une seule asymétrie avec le mobile : le service worker.

Prérequis

  1. Le même projet Firebase, avec une app Web enregistrée.
  2. Une clé VAPID (console Firebase > Cloud Messaging > Web Push certificates).
  3. Le service worker packagé, copié dans le dossier public de l'app — un navigateur ne peut recevoir de push onglet fermé qu'à travers un fichier statique servi à la racine du site : 
    cp node_modules/@gittestmag/izipush-sdk/web/firebase-messaging-sw.js public/firebase-messaging-sw.js

Le fichier ne se modifie jamais à la main

La configuration Firebase et l'URL de l'API izipush lui sont transmises par les paramètres d'URL au moment de l'enregistrement. Le même fichier convient donc à toutes les applications et à tous les environnements. Recopiez-le tel quel à chaque montée de version du SDK.

import { initPush } from '@gittestmag/izipush-sdk';

07

Brancher sur une application existante

Quand l'app a déjà sa pile push et ne veut du SDK que le rattachement à izipush.

Le jeton attendu est le jeton d'inscription FCM — sur Android et sur iOS Sur iOS, ce n'est pas le jeton APNs brut rendu par didRegisterForRemoteNotificationsWithDeviceToken : Firebase encapsule APNs et émet son propre jeton. Les deux ne sont pas interchangeables. Enregistrer un jeton APNs en le déclarant fcm est accepté sans erreur — izipush stocke la chaîne telle quelle — et tous les envois échouent ensuite en silence.

Trouver son cas

L'app utilise déjà…Le jeton à passerÀ faire
@react-native-firebase/messaging await messaging().getToken() Rien de plus : c'est exactement le jeton attendu, à passer dans firebaseToken.
APNs en direct (pas de Firebase) Le jeton APNs Passer token avec providerId: 'apns', et configurer une intégration APNs dans izipush (clé .p8 ou certificat).
Expo Notifications getExpoPushTokenAsync() Passer token avec providerId: 'expo' et configurer l'intégration Expo. Attention : getDevicePushTokenAsync() rend du FCM sur Android mais de l'APNs sur iOS — les deux ne se mélangent pas sous un seul providerId.
OneSignal L'identifiant d'abonné OneSignal Passer token avec providerId: 'one-signal' et configurer l'intégration correspondante.

Dans tous les cas : le même projet des deux côtés

Un jeton n'a de sens que pour le projet qui l'a émis. Le projet Firebase de l'app doit être celui dont le compte de service est configuré dans l'intégration push d'izipush. Deux projets différents, et les envois échouent — sans que rien ne le signale au moment de l'enregistrement.

La vérification tient en une comparaison : le project_id du google-services.json (ou le PROJECT_ID du GoogleService-Info.plist) doit être identique au Project ID de l'intégration FCM dans izipush. S'ils diffèrent, le fournisseur répond SenderId mismatch ou Requested entity was not found au premier envoi, et le jeton est retiré du profil.

Le point d'entrée dédié

@gittestmag/izipush-sdk/register n'expose que le rattachement, et ne charge ni Firebase ni Notifee : il s'importe dans une application qui n'a aucune de ces dépendances. L'app garde la main sur l'autorisation, l'affichage et la navigation. 

import { registerPushToken } from '@gittestmag/izipush-sdk/register';

// Le jeton vient de la pile push que l'app possède déjà.
const token = await messaging().getToken();

await registerPushToken(currentUser.id, {
  novuApiUrl: 'https://<host-izipush>/api',
  applicationIdentifier: '<identifiant public de l’environnement>',
  hmacHash,
  firebaseToken: token,          // le champ dit de quel jeton il s'agit
  // token, providerId: 'apns',  // pile push autre que Firebase
});
Le renouvellement du jeton reste à la charge de l'app C'est le seul point que le SDK ne peut pas reprendre : il n'écoute rien dans ce mode. Rappelez registerPushToken à chaque rotation, sinon le client devient injoignable au bout de quelques semaines, sans erreur visible. Les jetons ne sont pas remplacés mais ajoutés — un même client reste joignable sur plusieurs appareils.

Un jeton gardé en stockage local

C'est une bonne optimisation et une mauvaise source de vérité. La plateforme fait autorité, pas le stockage : relisez le jeton courant à chaque lancement, et ne réenregistrez que s'il a changé. Le stockage sert à éviter un appel inutile, jamais à remplacer la question. 

// à chaque lancement, après authentification
const courant = await messaging().getToken();          // la plateforme fait autorité
if (courant !== (await storage.get('pushToken'))) {
  await registerPushToken(userId, { ...config, firebaseToken: courant });
  await storage.set('pushToken', courant);
}

// et surtout, la rotation :
messaging().onTokenRefresh(async (jeton) => {
  await registerPushToken(userId, { ...config, firebaseToken: jeton });
  await storage.set('pushToken', jeton);
});
Sur iOS, le piège est le trousseau (Keychain) Contrairement à Android, le trousseau iOS survit à la désinstallation de l'app. Un jeton rangé dans react-native-keychain ou expo-secure-store est donc relu après une réinstallation — alors qu'iOS en a émis un nouveau et que l'ancien est mort. L'app réenregistre consciencieusement un jeton invalide, et le client ne reçoit plus rien. Avec AsyncStorage ou UserDefaults, effacés à la désinstallation, le problème ne se pose pas.

Trois autres moments où iOS invalide un jeton sans prévenir

  • Restauration d'une sauvegarde sur un nouvel appareil.
  • Réinstallation de l'application.
  • Certaines mises à jour majeures du système.

Dans les trois cas, APNs révoque et Firebase émet un nouveau jeton d'inscription. Seuls getToken() au lancement et onTokenRefresh le voient — un jeton relu en stockage, non.

À noter aussi : sur iOS, aucun jeton n'existe tant que l'enregistrement APNs n'a pas abouti. Lire le stockage au démarrage, avant l'autorisation, ne rend donc rien la première fois. Et le simulateur iOS n'émet pas de jeton du tout : un test qui « ne marche pas » commence souvent là.

Un jeton mort ne s'accumule pas

izipush ajoute les jetons plutôt que de les remplacer — un client reste joignable sur plusieurs appareils. Un jeton devenu invalide n'encombre pas pour autant le profil : au premier envoi, l'erreur du fournisseur (BadDeviceToken, ExpiredPushToken, NotRegistered…) le fait retirer automatiquement, et la trace apparaît dans le fil d'activité du message. Le client reste néanmoins injoignable tant qu'un jeton valide n'a pas été enregistré à la place.

Remonter les ouvertures soi-même

Dans ce mode, le SDK n'écoute pas les appuis : sans cet appel, les taux d'ouverture push des rapports restent à zéro. Passez-lui les données de la notification depuis le gestionnaire de l'app — il y cherche l'identifiant de message posé par izipush et ignore tout le reste, sans appel réseau. 

import { reportOpened } from '@gittestmag/izipush-sdk/register';

// dans le gestionnaire d'appui existant de l'app
await reportOpened({ novuApiUrl, applicationIdentifier }, notification.data);
08

API commune

Les trois premières fonctions existent à l'identique sur les deux plateformes et renvoient les mêmes types.

initPush(userId, config): Promise<IzipushSubscription | null>

Enregistre le jeton, met en place l'affichage et la remontée des ouvertures. Deux usages, selon que l'app détient déjà un jeton ou non : 

// 1. L'app a déjà son jeton : il est enregistré tel quel, AUCUNE autorisation n'est demandée.
await initPush(currentUser.id, { ...config, firebaseToken: monJeton });

// 2. L'app n'a pas de jeton : le SDK demande lui-même l'autorisation.
await initPush(currentUser.id, config);

Renvoie null si l'autorisation est refusée ou la plateforme non compatible.

initPermissions(userId, config): Promise<IzipushSubscription | null>

Demande l'autorisation, récupère le jeton de la plateforme et l'enregistre. C'est exactement ce qu'appelle initPush lorsqu'aucun token ne lui est passé — l'exposer séparément permet de choisir le moment de la demande (section 09).

getPermissionStatus(): Promise<IzipushPermission>

État actuel de l'autorisation, sans rien demander.

ValeurSignification
'granted'Autorisé : les notifications arrivent.
'denied'Refusé. Redemander ne sert à rien : seul un passage par les réglages le change.
'undetermined'La question n'a jamais été posée — le seul état où une demande peut aboutir.
'unsupported'La plateforme ne sait pas recevoir de push (voir section 02).

registerBackgroundHandler(config): void — natif uniquement

Enregistre l'affichage des notifications reçues app fermée ou en arrière-plan, et la remontée des appuis. À appeler une seule fois, au niveau module de index.js. N'existe pas côté web : son équivalent est le service worker packagé.

09

Choisir le moment de la demande

La question ne se pose qu'une fois. C'est la décision produit la plus lourde de conséquences de toute l'intégration.

Sur iOS comme sur Android 13+ et dans tous les navigateurs, un refus est définitif : le système ne repose plus la question, et seul un passage par les réglages peut le revenir dessus — ce que presque personne ne fait. Demander au premier lancement, avant que l'utilisateur ait compris ce qu'il y gagne, c'est donc perdre définitivement une partie de l'audience joignable.

Le schéma recommandé

import { getPermissionStatus, initPermissions, initPush } from '@gittestmag/izipush-sdk';

// À la connexion : on enregistre ce qu'on a déjà, sans jamais demander.
const status = await getPermissionStatus();
if (status === 'granted') {
  await initPush(currentUser.id, config);
}

// Plus tard, au bon moment : après une première transaction, sur un écran
// « soyez prévenu quand … », jamais à froid.
if (status === 'undetermined') {
  const accepte = await montrerEcranDExplication();   // écran maison, pas le SDK
  if (accepte) await initPermissions(currentUser.id, config);
}

// 'denied' : ne rien demander. Au mieux, expliquer où réactiver, dans les réglages.
// 'unsupported' : masquer l'option.
Ne demandez jamais deux fois Appeler initPermissions alors que le statut est 'denied' ne produit aucune boîte de dialogue — l'appel retourne simplement null. C'est sans danger, mais sans effet : c'est l'écran de réglages qu'il faut proposer.
10

Statistiques d'ouverture

Automatique, sur les deux plateformes. Rien à appeler.

L'appui sur une notification de campagne est signalé au CRM izipush, ce qui alimente les taux d'ouverture des rapports :

  • Mobile — par Firebase et Notifee, que l'app soit au premier plan, en arrière-plan ou fermée.
  • Web — par le service worker, seul endroit qui reçoit l'appui que la notification ait été affichée par la page ou par lui.

Ce qui n'est pas mesuré

Une notification affichée mais jamais touchée ne peut pas être comptée : aucune plateforme ne le permet. Un taux d'ouverture push est donc un taux d'appui — il est fiable, mais plus bas qu'un taux d'ouverture email, qui compte lui des affichages. Les deux ne se comparent pas.

Les notifications hors campagne ne portent pas d'identifiant de message et ne déclenchent aucun appel réseau. Une statistique perdue (réseau coupé) n'a jamais d'effet visible pour l'utilisateur.
