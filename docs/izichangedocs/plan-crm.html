03

Ce que le code nous impose

Relevé dans le fork en préparant ce plan. Chaque point est déjà intégré aux lots.

ConstatConséquence dans le plan
L'API Novu n'ajoute que 100 membres par appel à un topic.Le CRM écrit les membres directement par le repository, en masse : pas 10 000 appels pour une liste de 1 M.
En production, Novu ne crée pas les index automatiquement.Les index CRM sont créés explicitement au démarrage (Lot 0), sinon chaque segment parcourrait 1 M de documents.
Les files Novu n'ont pas de priorité, mais BullMQ la transmet telle quelle.Une ligne dans queueJob() : priorité haute si le workflow est critique (Lot 2).
Aucun repli ni relance sur erreur fournisseur email ; aucun statut « reporté ».Aiguilleur dans l'envoi email + nouveau statut « reporté » qui replanifie le job (Lot 3).
Le dashboard n'appelle que l'API Novu.Les écrans CRM parlent aux modules CRM de apps/api ; crm-ingest n'expose que l'ingestion.
Les droits (RBAC) sont inactifs en édition communautaire.Sans impact en V1 (droits de lancement reportés). À construire plus tard si besoin.
Une plainte email est enregistrée comme un succès ; les webhooks ne modifient pas le message.Notre accroche d'engagement traite la plainte comme une exclusion d'adresse (Lot 3).
La push contient déjà l'identifiant du message.Le SDK n'a qu'à le renvoyer à l'ouverture : pas de changement côté envoi (Lot 4).
RabbitMQ n'existe nulle part dans le repo.Ajout de la bibliothèque et d'un conteneur RabbitMQ en dev (Lot 0-1).

Méthode

Tests

Tests unitaires à côté du code (mocha pour api/worker, jest pour les libs). Pour chaque lot, un scénario de bout en bout avec des événements simulés au format actuel d'Izichange.

Machine locale

Compilations et tests lancés un par un avec un plafond mémoire : c'est ce qui avait fait planter le poste.

Commits

Commits locaux sur crm, un par tâche. Tu pousses (le push vers un nouveau dépôt m'est bloqué).

Mises à jour Novu

Code CRM isolé ; chaque point d'accroche est commenté // izipush-crm pour les retrouver à chaque fusion.
