izipush · architecture CRM · V1

izipush CRM — architecture cible

izipush, le fork de Novu, devient un CRM complet : il connaît les clients d'Izichange et leur activité, construit des segments, porte les templates email, lance des campagnes push et email, et rend compte de chaque envoi jusqu'au client. Izichange n'a qu'un rôle : émettre ses événements. Tout le reste vit dans le fork.

Ce que la V1 doit savoir faire, et ce qui est volontairement laissé pour après.

03

Principes structurants

Les décisions qui conditionnent tout le reste.

DécisionPourquoi
Tout dans MongoDB, pas de Postgres dans izipush Novu est entièrement construit sur Mongo (couche d'accès, schémas, agrégations). Une deuxième base obligerait à synchroniser les clients entre deux systèmes et à faire des jointures inter-bases pour chaque segment. Une seule base, une seule vérité.
Le profil client = le subscriber Novu subscriberId = user_id Izichange. Les templates lisent {{subscriber.firstName}} directement, les filtres d'étape Novu lisent subscriber.data.* sans rien ajouter. Plus de table users à part.
L'activité est séparée du profil Le subscriber est relu à chaque étape de chaque workflow et mis en cache ; y écrire à chaque transaction viderait le cache en permanence. Et une activité rangée par jour dans le profil ne peut pas être indexée pour la segmentation.
Le journal est la source de vérité, les agrégats sont recalculés Chaque agrégat (jour, cumul) est réécrit ($set) à partir du journal, jamais incrémenté ($inc). Un événement reçu deux fois ou un plantage en cours de traitement ne peut donc pas fausser un total : rejouer donne toujours le même résultat.
Pas de replica set requis Sans transactions multi-documents, chaque écriture est soit atomique sur un seul document, soit rejouable (index uniques, recalcul). Novu retombe déjà sans transaction sur un Mongo seul (base-repository.ts). Le passage à un replica set reste recommandé plus tard, pour la disponibilité.
Le contenu vit dans le workflow, la campagne dit qui et quand On ne duplique pas le moteur d'envoi de Novu : une campagne résout une audience, l'écrit dans un topic, puis déclenche un workflow existant. Fan-out, étapes, canaux et retries restent ceux de Novu.
Tout le code CRM dans le fork, dans des modules isolés Modules préfixés crm, collections préfixées crm_, modifications du cœur Novu réduites aux points d'accroche (choix du fournisseur, champs d'intégration). Les mises à jour de Novu restent fusionnables.

05

Ingestion des événements · crm-ingest

Un service du monorepo, dans son propre conteneur, qui transforme chaque événement d'Izichange en profil et activité à jour. Il se branche sur les flux qui alimentent déjà MailWizz.

Branchement sans effort

Un exchange topic alimente plusieurs files : on lie notre propre file à l'exchange existant, MailWizz continue de recevoir. Keycloak : notre endpoint en seconde destination.

Ordre d'arrivée

Chaque champ garde la date de sa dernière mise à jour ; un événement plus ancien ne l'écrase pas (kyc.submitted arrivé après kyc.approved est sans effet).

Client inconnu

Une transaction peut arriver avant l'inscription : un profil minimal est créé, puis complété à l'arrivée de l'inscription.

Totaux reçus ignorés

volumeJour, nbreOpMois, walletAvailable… ne sont pas utilisés : tout est recalculé depuis les transactions.

Événements attendus

Uniquement des actions, publiées au moment où elles se produisent. Jamais d'événement déclenché par le temps (« inactif depuis 30 j »), jamais de total pré-calculé : tout cela se déduit de notre côté.

06

Flux · segments

Un segment = des conditions. Figé ou non, il est résolu de la même façon ; seule la date de résolution change.

Construction

  1. Le constructeur propose les champs de crm_fields : champs du profil (pays, KYC, date d'inscription, cumul à vie…) et champs d'activité (nombre de transactions ou volume sur N jours, par produit ou tous produits).
  2. Les conditions forment un arbre (ET / OU / NON). Exemple : pays ∈ {CI, SN} ET KYC = validé ET volume crypto sur 30 j > 500 USD.
  3. Aperçu en direct : le nombre de clients correspondants est calculé à chaque modification.
  4. Case « figer » cochée : à l'enregistrement, le segment est résolu une fois et ses membres écrits dans le topic Novu segment:{id}, avec frozen_at. Décochée : rien n'est stocké, la résolution a lieu à chaque exécution de campagne.

Résolution d'une audience

Les conditions sont séparées en deux familles, exécutées chacune sur ses index, puis croisées :

// 1. Conditions d'activité → identifiants (fenêtre indexée sur day)
crm_activity_daily.aggregate([
  { $match: { day: { $gte: J-30 }, product: "crypto" } },
  { $group: { _id: "$subscriberId", vol: { $sum: "$vol_usd" } } },
  { $match: { vol: { $gt: 500 } } }
])

// 2. Conditions de profil + garde-fous → filtre sur subscribers
{ "data.country_code": { $in: ["CI","SN"] }, "data.kyc_status": "validated",
  "data.isDeleted": { $ne: true }, subscriberId: { $in: <résultat 1> } }

On commence par la famille la plus sélective. Les résultats sont lus en flux (curseur) et écrits par lots, jamais chargés en mémoire d'un bloc.

Figer fixe qui on vise, pas qui on a le droit de contacter. Même pour un segment figé, les garde-fous (client supprimé, consentement retiré, email invalide) sont appliqués au moment de l'exécution.
07

Flux · campagnes

Une exécution de campagne est une machine à états : chaque étape peut être rejouée après un plantage sans rien envoyer deux fois.

DéclencheurQuand ?Clic « lancer », date programmée, cron récurrent (job répétable BullMQ).
→
resolvingQui ?Membres du segment figé, ou résolution des conditions (§06).
→
resolvingExclusionsSupprimés, sans consentement marketing, sans canal joignable. Comptées par motif.
→
triggeringTopic du runcampaign:{id}:{runId} rempli par lots ; index unique = reprise sans doublon.
→
sendingUn seul triggerWorkflow déclenché sur le topic, transactionId = runId. Novu fait le fan-out.
  1. Création de crm_campaign_runs en resolving. Un run déjà en cours pour la même échéance n'est pas recréé (clé unique campagne + échéance).
  2. Résolution et exclusions, écriture des membres dans le topic du run. Relancer cette étape réécrit les mêmes membres (index unique), sans doublon.
  3. Passage en triggering, puis un seul appel de déclenchement sur le topic, avec transactionId = runId. Novu rejette un déclenchement dont le transactionId a déjà produit des jobs : une reprise après plantage ne renvoie pas la campagne. Cette vérification n'est pas atomique (lecture puis rejet), c'est donc l'état du run qui garantit qu'un seul worker déclenche.
  4. Novu exécute le workflow pour chaque membre : étapes, délais, canaux, retries — rien de nouveau ici.
  5. Passage en done quand plus aucun job du run n'est en attente ; les statistiques sont calculées (§09).
Priorité aux messages critiques. Les files de Novu n'ont pas de priorité : un OTP déclenché pendant une campagne à 1 M attendrait derrière tous ses jobs. Dans le fork, les jobs des workflows critiques (OTP, reçus, sécurité) sont ajoutés avec une priorité haute BullMQ et doublent la campagne dans la file. 
file standard :  [OTP] ← passe devant    [camp][camp] … [camp]
Envoyer une campagne par lots (goutte-à-goutte) est reporté : à évaluer en production.

Les campagnes sur événement sont le seul cas sans topic : elles sont évaluées client par client dans le job de dérivation (§05, étape 7).

08

Flux · envoi email multi-fournisseur

Plusieurs fournisseurs email, chacun avec ses limites ; le worker choisit pour chaque email celui qui a encore du quota.

Configuration

À l'ajout (ou la modification) d'un fournisseur email dans le dashboard, trois limites optionnelles — par seconde, par heure, par jour — un poids (répartition entre fournisseurs disponibles) et un interrupteur « participe à l'aiguillage ».

À l'envoi

  1. L'étape email du workflow arrive dans le worker. Novu choisit normalement le fournisseur « principal », ou celui imposé via integrationIdentifier. On insère l'aiguillage à cet endroit.
  2. L'aiguilleur lit les compteurs Redis de chaque fournisseur éligible (fenêtres seconde / heure / jour) et en tire un parmi ceux qui ont du quota, selon leur poids. La réservation du quota est atomique (script Lua) : deux workers ne peuvent pas dépasser la limite ensemble.
  3. Tous les fournisseurs sont pleins : le job est replanifié après un délai, pas mis en échec. L'envoi ralentit, il ne se perd pas.
  4. Un fournisseur répond en erreur de façon répétée : il est mis de côté quelques minutes (disjoncteur) et l'envoi repart sur un autre.
  5. Chaque envoi incrémente les compteurs du fournisseur, repris par l'écran de monitoring.
Plusieurs fournisseurs augmentent le débit et la résilience, mais ne protègent pas à eux seuls du spam. Gmail et Outlook jugent surtout la réputation du domaine d'envoi. Il faut : SPF, DKIM et DMARC configurés sur chaque fournisseur, un sous-domaine dédié au marketing (ex. news.izichange.com) pour ne jamais dégrader la délivrabilité des emails transactionnels, une montée en volume progressive, et l'exclusion automatique des adresses en bounce ou en plainte.

Onglet Rapports

  • Liste des exécutions de chaque campagne : date, statut, audience, exclus (par motif), envoyés, délivrés, ouverts, cliqués, échecs.
  • Détail d'une exécution : les mêmes chiffres par canal, et la liste des clients visés (le topic du run), filtrable.
  • Détail d'un client : chaque message reçu, les étapes du workflow avec leurs horodatages (executiondetails), et s'il a ouvert, vu ou cliqué.
  • Les statistiques d'un run sont recalculées depuis messages et crm_engagement (par transactionId), jamais incrémentées : elles restent justes même si un webhook arrive deux fois.

Écran de monitoring des fournisseurs

Quotas

Consommation en temps réel face aux limites (seconde / heure / jour), par fournisseur. Source : compteurs Redis.

Débit

Emails et push envoyés par minute sur les dernières heures, par fournisseur. Source : crm_provider_usage.

Délivrabilité

Taux de délivrance, de bounce et de plainte par fournisseur, avec seuils d'alerte (ex. bounce > 5 %, plainte > 0,1 %).

Santé

Taux d'erreur, latence, état du disjoncteur, dernières erreurs brutes. Pour le push : part de tokens invalides renvoyés par FCM.

Le worker verse chaque minute les compteurs Redis dans crm_provider_usage (écriture $set de l'heure en cours, rejouable).

10

Consentement, désinscription, suppression

Transactionnel ou marketing

  • Workflows transactionnels (OTP, reçus, alertes de sécurité) : marqués critiques dans Novu — le client ne peut pas s'en désabonner. NATIF
  • Workflows marketing : non critiques, soumis aux préférences du client par canal, et à data.marketing_optin. NATIF ENRICHI

Désinscription

  1. Chaque email marketing contient un lien {{unsubscribe_url}} : une URL publique portant un jeton signé (client + environnement + expiration).
  2. L'en-tête List-Unsubscribe avec désinscription en un clic est ajouté aux emails marketing — Gmail et Yahoo l'exigent pour les envois en volume.
  3. Au clic, la route publique vérifie la signature et coupe la préférence marketing email du client. Aucune connexion requise.
  4. Un bounce définitif ou une plainte pose data.email_suppressed = true : l'adresse est exclue de tout envoi marketing.

Suppression d'un compte

  • L'événement de suppression pose data.isDeleted = true. Le profil, l'activité et l'historique sont conservés.
  • Les tokens push du client sont effacés en même temps : même un déclenchement direct hors campagne ne peut plus atteindre ses appareils.
  • Le client est exclu de toute résolution d'audience, y compris des segments figés.
11

Reprise de l'existant

Izichange fournit une fois l'export brut de ses tables users et transactions. Toute la transformation est faite de notre côté.

  1. Date de coupure D (minuit). Izichange commence à publier les événements temps réel à partir de D ; notre file les garde en attente.
  2. Export des deux tables jusqu'à la veille de D incluse, déposé sur un stockage partagé (S3 ou SFTP) — jamais par email : elles contiennent des données personnelles.
  3. Chargement brut dans deux collections temporaires (crm_import_users, crm_import_transactions).
  4. Clients → subscribers : correspondance colonnes → champs (définie à réception de l'export), écriture en masse par lots avec upsert sur subscriberId.
  5. Transactions → crm_activity_daily : agrégation par client, jour et produit (montants déjà en USD), écriture par $merge.
  6. Faits du profil : first_tx_at, last_tx_at, lifetime_* et {produit}_activated_at calculés depuis le daily et posés sur chaque subscriber.
  7. Contrôles de rapprochement : nombre de clients, nombre de transactions et volume par mois, comparés à l'export. Les collections temporaires sont supprimées une fois validées.
  8. Démarrage de la consommation RabbitMQ : le temps réel prend le relais à partir de D.
Pas de double comptage possible. Une journée est alimentée soit par l'import (avant D), soit par les événements (à partir de D), jamais par les deux. Toutes les étapes sont des upserts : le script peut être relancé.

Faisabilité & volumétrie

Ordres de grandeur à 1 M de clients. Les hypothèses d'activité sont à confirmer avec l'export réel.

ÉlémentEstimationCommentaire
Subscribers1 M documents, quelques Go avec indexVolume courant pour Mongo.
crm_activity_daily~200 000 lignes / jour → ~10 Go / an avec indexHypothèse : 20 % de clients actifs par jour, plusieurs produits. Archivage des vieilles années possible, pas nécessaire avant plusieurs années.
crm_eventsTaille bornée par le TTL de 180 jLes journées passées du daily sont définitives : le journal n'est plus utile au-delà.
Résolution d'une audienceÀ mesurer — objectif < 2 min sur 1 MDépend des index et de la sélectivité des filtres : benchmark à faire sur 1 M de clients fictifs.
Fan-out d'un topic de 1 MÀ mesurerNovu sait déclencher un topic ; le débit à 1 M dépend du nombre de workers. À inclure dans le benchmark.
Durée d'une campagne emailDictée par les limitesExemple : 2 fournisseurs à 50 emails/s = 100/s → 1 M d'emails en ~2 h 45. Ce sont les limites fournisseurs qui fixent la durée.

Risques

  • Fusion des mises à jour Novu : limitée en gardant le CRM dans des modules et collections à part, et en réduisant les modifications du cœur aux points d'accroche listés en §12.
  • Mongo sur un seul nœud : pas de risque de cohérence (tout est rejouable), mais un risque de disponibilité. Replica set recommandé avant la mise en production à 1 M.
  • Débit pendant une grosse campagne : les messages critiques passent devant grâce à la priorité ; si la file reste trop longue en production, on ajoutera l'envoi par lots.
  • Délivrabilité email : un démarrage à pleine vitesse sur un domaine neuf finit en spam. Montée en volume à planifier.
